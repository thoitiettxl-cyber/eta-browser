# Execution Plan: Eta Browser v1.0.0 Branding And Signed Release

Date: 2026-08-14

## Status

Completed

## Outcome

Eta Browser has a distinctive launcher logo, a repository-owned GitHub Actions path that builds and verifies a persistently signed release APK, durable signing credentials configured without entering Git, and a reviewable v1.0.0 release candidate that is published only after installed-device acceptance.

## Context

- `README.md`: application identity and component overview.
- `app/build.gradle.kts`: version `1.0.0` / code `1` and release build type.
- `app/src/main/AndroidManifest.xml`: launcher application metadata.
- `.github/workflows/ci.yml`: authoritative Android/CLI/Pi checks; currently debug-only.
- `docs/RELEASING.md`: signing, evidence, disclosure, and publication requirements.
- `docs/VALIDATION.md`: CI authority and installed-device acceptance gate.

## Scope

In scope:

- Create one high-resolution Eta Browser logo master and Android launcher/adaptive icon resources.
- Configure release signing from GitHub Secrets and a non-secret alias variable.
- Create a manually dispatched GitHub Actions workflow that builds, verifies, hashes, and uploads the signed release APK and release evidence.
- Generate one long-lived RSA-4096 Android signing key, retain a private local recovery copy, and configure repository Secrets/Variable without exposing values.
- Validate locally available host checks, use GitHub Actions for Android proof, merge through a PR after checks pass, and provide the exact signed artifact for device testing.
- After explicit successful installed-device confirmation, publish GitHub Release `v1.0.0` with the verified APK and required disclosures.

Out of scope:

- Google Play publication or Play App Signing enrollment.
- Automatic GitHub Release publication before installed-device acceptance.
- Application ID migration, protocol changes, or unrelated product changes.

## Approach

1. Generate and review a minimal blue eta/browser logo, then derive repository-native Android launcher assets.
2. Add environment-backed Gradle release signing with no credential fallback or committed secret material.
3. Add a manual signed-release workflow that materializes the keystore only under the runner temporary directory, runs required checks and `assembleRelease`, verifies signing, records SHA-256/certificate/source/run metadata, and uploads immutable candidate artifacts.
4. Generate the signing key under `/root/.config/eta-browser/signing/`, set restrictive permissions, configure GitHub Secrets/Variable, and verify only names/metadata.
5. Run focused host validation and structural secret-leak checks, review the diff, commit, push, and create a PR.
6. Require successful GitHub Actions checks before squash merge. Dispatch the signed-release workflow from merged `main`, download the exact artifact, and report its evidence for installation.
7. Wait for installed-device acceptance. Publish the same artifact as GitHub Release `v1.0.0` only after the user confirms success, then complete this plan.

## Risks And Recovery

- Losing the signing key prevents future APK updates. Keep a restrictive local recovery copy and require an additional off-device backup; GitHub Secrets are not recoverable backups.
- Logging or committing credentials would compromise signing. Pass secrets only through GitHub secret contexts/environment, mask derived values, keep the keystore under runner temporary storage, and scan the final diff/worktree.
- An invalid launcher asset can render poorly under adaptive masks. Preserve a large safe zone and provide adaptive, round, and legacy resources.
- A minified release can differ from debug behavior. Build through CI, verify the exact signed APK, and require installed-device acceptance before publication.
- If the PR is rejected or CI fails, do not merge; revise on the branch. If signing configuration is compromised, delete/replace the affected GitHub Secrets before any public release and generate a new key while no release has yet shipped.
